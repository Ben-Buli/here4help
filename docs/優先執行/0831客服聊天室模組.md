超讚，我幫你把「一案一房 + 最多 3 個並行客服房」整套 MVP 規格敲定，並把 任務爭議（dispute） 跟 一般客服（support） 清楚分流、列表呈現、上限規則、指派（claim/assignee）與資料表/ API 一次講清楚：

⸻

1) 上限策略（結論）
	•	一般客服（support）：
	•	採「每位使用者同時最多 3 個 未結案房」上限（open/in_progress/waiting_customer 都算在內）。
	•	這是 /contact-us 產生的案件。
	•	任務爭議（dispute）：
	•	不列入上面 3 間的上限（因為是任務生命週期的一部分，不能阻擋）。
	•	每個任務最多 1 個進行中的爭議房（per task，避免重複申訴）。
	•	列表顯示：在客服列表一起顯示，但用 Tabs 區分：All / Support / Dispute（預設 All）。
	•	這樣做法：
	•	不會因為客訴上限卡住爭議流程；
	•	又能限制 /contact-us 濫用而炸房。

⸻

2) 角色與對話對象
	•	房間成員：
	•	使用者（Flutter App 端）
	•	唯一受理管理員（PHP Web Admin 端）
	•	指派模式（Claim）：
	•	誰先按 Accept/Claim，assignee_admin_id = 該管理員，之後就形成 1v1。
	•	其他管理員在列表可見該房與負責人，但 不可發訊息（view-only）。
	•	可提供 Transfer 將案件轉派給另一位管理員（寫 admin_log + system message）。
	•	訊息權限（MVP）：
	•	只有「使用者 與 assignee 管理員」能發訊息；
	•	其他管理員只能查看；
	•	（進階）若要補「內部備註」，另做 kind='internal' 僅 admin 可見，但 MVP 可先不做。

⸻

3) 資料結構（MVP 版）

3.1 chat_rooms（沿用，補欄位）
	•	id
	•	type ENUM('support','dispute','task')
	•	title（建議帶票號，如 [S-1023] Subject / [D-558] Task #449 dispute）
	•	creator_id（發起人 user_id）
	•	participant_id（保留給 task 房；support/dispute 不用）
	•	task_id NULL（dispute 會綁任務）
	•	assignee_admin_id NULL（誰 claim 了）
	•	status ENUM('open','in_progress','waiting_customer','resolved','closed')（support/dispute 也統一用這個狀態）
	•	created_at/updated_at/closed_at

索引：(type,status,creator_id)、(type,task_id)。

3.2 support_events（建議開）
	•	id
	•	user_id
	•	room_id
	•	subject
	•	category（payment/account/bug/other）
	•	status（同步 chat_rooms.status）
	•	assignee_admin_id（同步 chat_rooms）
	•	created_at/updated_at/closed_at

（也可以只用 chat_rooms，不開 support_events，但有 event 表更好做報表）

3.3 dispute_cases（建議開）
	•	id
	•	task_id
	•	room_id
	•	initiator_user_id（誰按的 dispute）
	•	status（open/in_review/resolved/rejected/closed）
	•	assignee_admin_id
	•	created_at/updated_at/closed_at

唯一性：保證同一 task_id 同時最多 1 個 status in (open,in_review)。
（你也可以不開這張，直接靠 chat_rooms (type='dispute', task_id)，但有表更好審計）

3.4 chat_messages（沿用，補 kind）
	•	room_id
	•	from_user_id NULL（system 訊息時可為 NULL）
	•	kind ENUM('user','system')
	•	message TEXT
	•	created_at

未讀數：照你現在做法，僅計入對方的 kind='user' 訊息，system 不計。

⸻

4) 流程規劃

4.1 /contact-us（Support）
	•	使用者送出表單 → 檢查此使用者 未結案 support 房數量 < 3 才允許建立
	•	建立：
	1.	建 support_events（status=open）
	2.	建 chat_room(type='support')、title 帶票號，成員 = 使用者
	3.	尚未有 assignee，等待管理員 claim
	4.	建首則訊息（使用者填的描述）
	5.	system: ticket_created
	•	管理員後台列表：點「Accept」
	•	設 assignee_admin_id = 自己，status='in_progress'
	•	system: admin_X accepted the ticket
	•	管理員可切 waiting_customer（等使用者回覆）、resolved
	•	使用者端可按「Close」（closed）

4.2 任務聊天室 → Dispute（Dispute）
	•	使用者在任務房 Action Bar 按 Dispute → 填表單
	•	後端：
	•	檢查該 task_id 是否已有進行中 dispute 房，如有 → 直接導向該房（避免重複）
	•	否則：
	1.	將 tasks.status = 'dispute'（寫 task_logs）
	2.	新增 chat_room(type='dispute', task_id=...)
	3.	建立 dispute_cases（status=open）
	4.	system: task set to dispute
	•	管理員後台：同 support 流程，Accept 後成為 assignee，1v1 溝通。
	•	結案：
	•	管理員決定：
	•	resolved（有時伴隨點數轉移/退款流程）
	•	或 rejected（駁回）
	•	system: dispute resolved/rejected by admin_X
	•	如任務要一起變更狀態，請寫在同一 transaction

⸻

5) API（最小清單）

Support
	•	POST /support/tickets（建立）→ 檢查上限 3 → 回 room_id, ticket_id
	•	GET /support/tickets?status=open|closed（使用者/管理員分開視角）
	•	POST /support/tickets/{id}/accept（管理員 claim）→ 設 assignee + 狀態 + system msg
	•	POST /support/tickets/{id}/status（管理員：in_progress / waiting_customer / resolved）
	•	POST /support/tickets/{id}/close（使用者：close）
	•	POST /support/tickets/{id}/transfer（管理員轉派）

Dispute
	•	POST /disputes（由任務房發起，body: task_id, description）→ 建房/建 case/改任務狀態
	•	POST /disputes/{id}/accept（管理員 claim）
	•	POST /disputes/{id}/resolve（管理員結案）
	•	POST /disputes/{id}/reject（管理員駁回）

聊天訊息沿用你現有的 /chat/messages / WebSocket 通知。

⸻

6) Flutter / Admin Web 端 UI 建議（MVP 快速做）

Flutter（使用者）
	•	/contact-us：
	•	置頂「New Ticket」按鈕（不足 3 間才顯示），下方列表（Open/Closed tabs）
	•	卡片上顯示：[#S-xxx] subject · status · unread
	•	ChatDetail：若 type='support' | 'dispute' → Action Bar 顯示「Close（support）」或「查看判定說明（dispute）」
	•	Dispute 入口：任務房 Action Bar 的 Dispute → 表單 → 成功後導向 dispute 房

Admin（PHP Web）
	•	Issues List：All / Support / Dispute tabs，顯示 assignee（或「Unassigned」）
	•	房內：未指派顯示「Accept」；指派後顯示 assignee
	•	Chat 視窗：非 assignee 不提供輸入框（read-only）

⸻

7) 權限 & 檢查
	•	支援「每使用者 同時最多 3 間 support 房」：

SELECT COUNT(*) FROM chat_rooms 
WHERE type='support' AND creator_id=:userId 
  AND status IN ('open','in_progress','waiting_customer');


	•	每任務最多一個進行中 dispute：

SELECT COUNT(*) FROM chat_rooms 
WHERE type='dispute' AND task_id=:taskId 
  AND status IN ('open','in_progress','waiting_customer');


	•	建立新房前先檢查上述條件，不符合就回 409/422。

⸻

8) 系統訊息（建議字典）
	•	ticket_created / ticket_accepted / ticket_waiting_customer / ticket_resolved / ticket_closed
	•	dispute_created / dispute_accepted / dispute_resolved / dispute_rejected

全部 kind='system'，不計未讀。

	1.	dispute 結案 是否會引發自動點數轉移/扣退？（若有，需要與既有付款流程串起來）
	2.	支援 轉派 規則：誰可以轉派？（super_admin only？或 assignee/任一 admin）
	3.	support 的 主旨/分類 欄位是否固定選單？（我預設 payment/account/bug/other）
	5.	列表是否要顯示 未讀數？（建議顯示，利於客服優先處理）

10) 快速落地提示
	•	Flutter：沿用你現有 chat 架構，新增 type='support'|'dispute' 的分支與入口即可。
	•	Admin PHP：
	•	列表頁 SELECT + claim 兩個 API 先做，就能跑 MVP。
	•	記得在 claim/transfer/resolve/reject/close 都寫 admin_logs + system message。
