### 客服聊天模組（先行處理）— 沿用 chat_rooms.type='support' 的最新對齊方案

- 決策落點（更新）
  - 房型維持: 使用 `chat_rooms.type='support'` 搭配通用 `chat_messages/chat_reads`
  - 事件資料: 使用 `support_events`、`support_event_logs`
  - 事件狀態（資料表）: `status` enum('submitted','in_progress','resolved')，預設 `submitted`
  - /chat/detail 動作:
    - 新增「issue」：開 Dialog 顯示客服事件 Timeline（由 `support_event_logs` 聚合）
    - 新增「solved」：詢問是否結束事件，必填五星評分(1-5)＋評論，送出後寫入 `rating`、`review`，並將事件狀態更新為最終結案（資料表寫入 `resolved`，UI 可顯示為 Solved）
  - 不含任務資料: 支援房不讀取 tasks/應徵相關資料、也不顯示task狀態alert bar，僅依聊天室＋事件表

### 五、風險/邊界

- `chat_rooms.participant_id` 若非空，接手需保護：已接手則拒絕再次 Claim(在管理員後台如果已有接手管理員，無法進入該聊天室，也沒有相關的按鈕進入聊天室)
- 客戶端與管理端時間線排序以 `support_event_logs.created_at`，需補在無 `submitted` 日誌時，使用事件 `created_at` 兜底
- 只讀控制需雙向（前端禁用＋後端拒發送），避免繞過
- 評分/評論與結案狀態需一致，建議統一在結案流程完成

## 重構為平台分區說明（Flutter App / Admin Web）

### Flutter App

- API（依現有資料庫結構）
  - 建立事件：`POST /api/support/create_issue.php`（新增）
  - 查事件/時間線：`GET /api/support/events.php?chat_room_id=:id`
  - 結案（評分＋評論必填）：`POST /api/support/events_close.php`

- 後端與前端資料對接邏輯
  - 建立事件：
    - request：`{ title, description }`
    - response：`{ room_id, event_id }`
    - 後端動作：
      1) 若不存在支援房，建立 `chat_rooms(type='support', creator_id=me, participant_id=NULL)`
      2) 建立 `support_events(chat_room_id, user_id=me, admin_id=NULL, status='submitted', title, description)`
      3) 新增 `support_event_logs(event_id, old_status=NULL, new_status='submitted')`
      4) 新增 `chat_messages(room_id, kind='system', content='Support case created ...')`
  - 查事件/時間線：
    - response：`events[]`，每筆含 `status/title/description/rating/review/logs[]`
    - timeline：依 `logs[].created_at` 排序；若缺起始 log，前端以事件 `created_at` 補首節點
  - 結案：
    - request：`{ event_id, rating(1..5), review(non-empty) }`
    - 後端：更新 `support_events.status='resolved', rating, review, closed_at=NOW()`，寫 log（old→resolved）

- 前端 UI 架構
  - `/account/support/issue_status`：
    - 列表：僅顯示 `support_events.status != 'resolved'`
    - 空狀態文字：No active support cases
    - FAB：開新事件表單（Subject/Description 必填）
  - `/chat/detail`（support 房）：
    - Action：`issue`（timeline dialog）、`solved`（評分＋評論 dialog）
    - 當前狀態 `resolved` → 輸入/上傳區域 read-only

- 步驟串接（App）
  1) 使用者進入 issue_status → FAB → 送 `create_issue`
  2) 成功後取得 `room_id` 自動導航至 `/chat/detail?room_id=...`
  3) 在聊天室 action → `issue` 顯示時間線（讀取 `events.php`）
  4) 聊天互動 → 管理員接手後，狀態可能變為 `in_progress`
  5) 使用者點 `solved` → 評分+評論 → 送 `events_close.php` → 狀態 `resolved` → read-only

- 欄位處理重點
  - status：只允許 `submitted/in_progress/resolved`
  - rating：1..5 整數；review：非空字串
  - logs：顯示 old→new，並以 created_at 排序

### Admin Web

- API（依現有資料庫結構）
  - 列表：`GET /api/support/issues.php`（新增，聚合 chat_rooms+support_events+chat_messages）
  - 接手：`POST /api/support/claim.php`（新增）
  - 更新狀態：`PATCH /api/support/events.php`（既有；支援 `in_progress`、管理員 Close→`resolved`）

- 後端與前端資料對接邏輯
  - 列表聚合：
    - 基準：`chat_rooms.type='support'`
    - 最新事件（status/title/description）從 `support_events` 取（依 created_at DESC）
    - 最後訊息時間：`MAX(chat_messages.created_at)`
  - 接手：
    - request：`{ room_id }`
    - 後端：
      1) 更新 `support_events.admin_id=adminId, status='in_progress'`
      2) 若房間 participant_id 為 NULL → 設定為 adminId
      3) 新增 `support_event_logs(old→in_progress)`
  - 更新狀態：
    - request：`{ event_id, status }`（e.g. in_progress / resolved）
    - 後端：更新 `support_events.status` 並寫 log；若 `resolved` → 補 `closed_at=NOW()`

- 前端 UI 架構
  - IssuesView：
    - 篩選（type=support, status, search, pagination）
    - 欄位：room_id / type / status / title / user / last_message_at / actions
    - actions：
      - Claim（未接手時）→ 成功後變 Room（僅自己能進）
      - Wait（進行中調整）/ Resolve（結案）/ Close（等同 Resolve）

- 步驟串接（Admin）
  1) 進入 Issues → 載入 `support/issues.php`
  2) 選擇一筆點 Claim → `support/claim.php`
  3) 成功後按鈕變 Room → 進入聊天室（支援房）
  4) 視情況 PATCH 事件為 `in_progress` / `resolved`

- 欄位處理重點
  - 僅允許單一 admin 接手：若 participant_id 已存在且非本人 → 禁止再次 Claim
  - 結案由管理員改狀態亦為 `resolved`（統一命名）
